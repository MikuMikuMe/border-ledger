# Lunch Flow RBC integration design

Goal: Use the verified Lunch Flow Personal API RBC feed in the existing private Border Ledger website and Android app, with secure server credentials, explicit account selection, durable daily/manual sync, and unchanged existing history.

Verified feed: /api/v1/accounts has numeric IDs, name, institution_name, provider, status; currency can be null. /accounts/:id/transactions returns transactions and total; each row has id, accountId, signed amount (negative debit), currency, date, merchant, description, isPending. Initial real-account read succeeded for chequing and Visa. No real credentials or financial rows belong in repository fixtures.

Architecture: Add a Lunch Flow provider service with additive lunchflow_accounts mappings. Do not repurpose Plaid items, mobile connections, access tokens, or source identities. Expand the transaction/source-record source enums with a tested data-preserving SQLite migration. Keep LUNCHFLOW_API_KEY solely in the Worker secret (already installed). Both clients use existing authenticated server routes; mobile uses existing native bearer HTTP transport, never browser credentials or a JS API key.

API contract (same JSON on web /api/lunchflow and mobile /api/mobile/v1/lunchflow):
- GET /accounts -> {configured:boolean, accounts:[{providerAccountId:string,name:string,institution:string,currencies:string[],selected:boolean,accountId:string|null,kind:'chequing'|'savings'|'credit'|null,currency:string|null,lastSyncedAt:string|null,lastError:string|null}]}. Include disconnected/error accounts rather than silently presenting empty success. Discovery derives currencies from actual transactions when metadata is null.
- GET /accounts?status=local -> the same DTO for saved mappings, read only from D1 for bounded completion polling.
- POST /account-selection body {accounts:[{providerAccountId:string,currency:string,kind:'chequing'|'savings'|'credit'}]} -> {selected:number,queued:boolean}. Explicit whole-selection replacement; at most 25 accounts, validate against provider response and currency registry. Creates deterministic dedicated ledger accounts, never guesses a match to statement/Plaid history. Deselection stops future refresh; imported history remains. Mobile writes require idempotency-key.
- POST /sync -> {queued:boolean,accounts:number}. Sync all selected accounts; queue required, never claim success if no queue.
- No provider login operation inside Border Ledger: Lunch Flow connections are managed in Lunch Flow; show a link and clear copy. Integration is for this owner's Personal API, not a multiuser platform.

Sync requirements: scheduled daily and manual enqueue same handler; full provider response must be complete before publication (pagination per actual API, total completeness checked); timeouts and bounded payloads; safe sanitized errors; validate IDs, dates, amounts, currencies and account ownership before writing. Preserve signed amounts; classify using existing ledger classification. Source identity is provider+provider-account+transaction ID; repeat same snapshot is a no-op, provider correction updates only that Lunch row. No merchant/date/amount heuristic deduplication. Full-snapshot reconciliation may remove only absent provisional Lunch rows, never posted history. Selection/disconnection must fence in-flight/queued writes. API failure preserves last-good data and exposes error. Record last successful sync time only after commit.

UI: Preserve incumbent design. Website Accounts gets a Lunch Flow section with selected-account checkboxes, explicit currency/kind selectors, Save selection and Refresh actions, last sync/errors, and a manage-connection link. Mobile Accounts exposes equivalent native UI via native bearer-backed bridge methods; no external OAuth handoff, new browser auth, or secret input. Existing ledger/account/transaction/export/report screens show the new lunchflow source accurately. Do not claim recurring/subscription detection from this feed; the existing Plaid recurring feature remains separate.

Verification: real RBC API reads, backend/auth/idempotency/migration preservation tests, web and RN rendering/operation tests, root and mobile typechecks/tests/build, Android unit/build checks, CodeScene per changed source/precommit/branch gates, independent review, desktop+phone web rendering and Android emulator if available. Merge protected main via PR and wait for final validation/release/deployment, then verify production counts and repeat sync idempotency through authorized UI. Preserve local Android configuration and untracked files.
